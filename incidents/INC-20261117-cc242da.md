# Request details p95 864.7 ms: partner lookup on every request

## Summary
Production canary deployment cc242da84daa23f55afa9d7bf708d5134bf58c31 was automatically rolled back after exceeding its latency budget with a p95 of 755.4 ms (SLO target: ≤ 300 ms). The regression was caused by the verified driver feature (RSA-005), which performed an uncached 600 ms partner lookup on every request details query. Adding an in-memory cache with a 5-minute TTL eliminates the repeated external round trips while keeping driver verification accurate.

## Impact
- **Endpoint**: `GET /v1/requests/{id}` experienced severe latency degradation (p95 increased from 117.4 ms to 864.7 ms).
- **Users**: Roadside assistance members and dispatchers retrieving request details or tracking rescue status.
- **Duration**: 180 seconds (the full duration of the canary evaluation window before automatic rollback).
- **Traffic**: The canary received 1,916 requests out of 19,206 total requests (~10% of production traffic across 1 of 10 deployment replicas). Error rate remained at 0.0%.

## Root cause
In `services/api/app.py`, function `get_request`: every request details call synchronously queried the partner Driver Directory whenever a driver was assigned. In production, this external lookup incurs a 600 ms round trip (`PARTNER_LATENCY_MS=600`). Because request detail lookups account for ~45% of traffic, these synchronous blocking calls queued on the single canary pod and drove p95 latency to 864.7 ms.

```python
name = r.get("driver_name")
profile = driver_directory.lookup(name) if name else None
return {**r, "driver_verified": profile["verified"] if profile else None}
```

## Why tests did not catch it
In `services/api/driver_directory.py`, `PARTNER_LATENCY_MS` defaults to 0 in non-production environments (`LATENCY_S = int(os.environ.get("PARTNER_LATENCY_MS", "0")) / 1000`). Local test runs, CI checks, and standard pre-PR GKE sandboxes run against this instant 0 ms stub. Additionally, functional unit and UI test suites assert correctness on individual requests rather than measuring latency under concurrency or partner latency. Consequently, all 35 API tests and 14 UI tests passed without detecting the 600 ms delay.

## Fix in this PR
Introduced an in-memory cache (`_VERIFICATION_CACHE`) with a 5-minute TTL (`_VERIFICATION_TTL_S = 300.0`) in `services/api/app.py` via `_is_driver_verified()`.
Instead of querying the partner Driver Directory on every request, `get_request` checks the cache first. Only the initial lookup for a driver executes `driver_directory.lookup()`; subsequent requests within 5 minutes return from cache in under 1 ms.
Expected latency afterwards:
Because repeated lookups for assigned drivers hit the in-memory cache, `GET /v1/requests/{id}` p95 latency will drop back to baseline (~110–120 ms). Overall canary p95 latency will drop from 755.4 ms to approximately 130–140 ms, well within the 300 ms budget.

## Follow-ups
1. Run pre-PR sandbox load tests (`scripts/sandbox.sh load`) with production partner latency (`PARTNER_LATENCY_MS=600`) whenever PRs introduce or modify partner integrations.
2. Add automated latency regression assertions in CI for endpoints communicating with external partner systems.
3. Introduce a strict timeout and fallback mechanism for external partner directory calls to protect API responsiveness if the partner is slow or unreachable.
