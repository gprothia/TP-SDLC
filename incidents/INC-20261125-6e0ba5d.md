# Request details p95 609.5 ms: partner directory lookup on read path exceeds SLO budget

## Summary
Production canary deployment 6e0ba5dd4864566ca9fa872df8642c6b9580a9fd was automatically rolled back after exceeding its latency budget with an overall p95 of 609.5 ms (SLO target: ≤ 300 ms). The regression occurred because driver verification queried an external partner directory during request details queries on cold or unprimed replica caches, incurring a 600 ms simulated round trip under concurrent load. Resolving driver verification at driver assignment and seed time eliminates external lookups from the read path while preserving driver badge accuracy.

## Impact
- **Endpoint**: `GET /v1/requests/{id}` and overall canary traffic experienced latency exceeding the SLO budget (canary overall p95 reached 609.5 ms vs ≤ 300 ms target; request details p95 was 603.0 ms).
- **Users**: Roadside assistance members and dispatchers retrieving request details or monitoring rescue status.
- **Duration**: 180 seconds (the full duration of the canary evaluation window before automatic rollback).
- **Traffic**: The canary received 406 requests out of 4,259 total measured requests (~9.5% of production traffic across 1 of 10 deployment replicas). Error rate remained at 0.0%.

## Root cause
In `services/api/app.py`, function `get_request`: driver verification was performed dynamically during request details retrieval by querying `_is_driver_verified(name)`. On cold replicas or unprimed cache states, this triggers an external round trip to `driver_directory.lookup()`, which incurs 600 ms simulated partner latency (`PARTNER_LATENCY_MS=600`). Because request detail lookups account for 45% of traffic, concurrent unprimed calls blocked worker threads and drove p95 latency to 609.5 ms.

```python
name = r.get("driver_name")
verified = await _is_driver_verified(name) if name else None
return {**r, "driver_verified": verified}
```

## Why tests did not catch it
In `services/api/driver_directory.py`, `PARTNER_LATENCY_MS` defaults to 0 in non-production environments (`LATENCY_S = int(os.environ.get("PARTNER_LATENCY_MS", "0")) / 1000`). Local test runs, CI checks, and standard pre-PR GKE sandboxes run against this instant 0 ms stub. Additionally, functional unit and UI test suites assert correctness on individual requests rather than measuring latency under concurrency or partner latency. PR #11 only added runtime dependencies for `loadgen`, and pre-merge checks did not run the production canary load generator against `PARTNER_LATENCY_MS=600`.

## Fix in this PR
Moved driver verification from the request details read path to driver assignment and seed time:
- In `seed()`, seeded request `RSA-1001` is initialized with `"driver_verified": True` and pre-warms the cache at startup.
- In `create_request` (`POST /v1/requests`), new requests start with `"driver_verified": None` since no driver is assigned yet.
- In `update_request` (`PATCH /v1/requests/{id}`), driver verification is resolved and stored on the request once when a dispatcher assigns or changes `driver_name`.
- In `get_request` (`GET /v1/requests/{id}`), the pre-resolved `driver_verified` flag is returned directly from the request record without invoking partner lookups.

Expected latency afterwards:
Because request details reads no longer trigger external partner lookups, `GET /v1/requests/{id}` latency drops to under 2 ms. Under synthetic production load, overall p95 latency will drop from 609.5 ms to well under 30 ms, safely within the ≤ 300 ms SLO budget.

## Follow-ups
1. Run pre-PR sandbox load tests (`scripts/sandbox.sh load`) with production partner latency (`PARTNER_LATENCY_MS=600`) whenever PRs introduce or modify partner integrations.
2. Add automated latency regression assertions in CI for endpoints communicating with external partner systems.
3. Introduce a strict timeout and fallback mechanism for external partner directory calls to protect API responsiveness if the partner is slow or unreachable.
